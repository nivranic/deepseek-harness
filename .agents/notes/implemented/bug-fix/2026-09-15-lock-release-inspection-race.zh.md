# Agent Note: 锁在检查期间释放后的重试

Status: implemented

[English](2026-09-15-lock-release-inspection-race.md) | 中文

## 问题

独占创建遇到已有写锁时，Windows 可能返回 `EPERM`。持有者可能在竞争者检查锁是否存在之前移除锁。把随后出现的 `ENOENT` 当成永久权限失败，会拒绝本可获取已释放锁的操作。

## 决定

[`withFileLock`](../../../../packages/util/atomic-write/src/index.ts) 在 `EPERM` 后检查得到 `ENOENT` 时，允许立即重试一次独占创建。连续第二次未确认存在锁的 `EPERM` 保留创建错误。观察到已有锁后恢复普通有界竞争处理；其他检查失败保留原创建错误。竞争者从不移除其他写入方的锁。

## 考虑过的替代方案

**拒绝所有未确认的 EPERM。** 即使下一次独占创建能够成功，这也会让操作因释放竞态而失败。

**把所有 EPERM 当成竞争。** 这会延迟真实权限失败，并把它们报告成锁超时。有界重试区分可能的释放与持续失败，同时保留独占创建保证。

## 后果

设置与凭据写入方可以获取刚释放的锁，持续权限错误仍会拒绝。重命名重试、仅字符串写入、期限与孤儿锁恢复保持不变。[凭据存储决定](../architecture/2026-07-30-credential-boundaries-and-atomic-registration.zh.md) 保留其独立的职责划分与防止陈旧状态覆盖的保证。

验证必须把持有者的 unlink 放在创建失败与检查之间，观察操作恰好成功一次及锁清理，并拒绝连续无锁错误和其他检查失败。该竞态使用确定性的文件系统故障注入，不证明 Windows 权限被改变或真实权限失败能够恢复。
