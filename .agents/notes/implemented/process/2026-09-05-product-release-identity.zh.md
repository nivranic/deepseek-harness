# Agent Note: 跨平台统一应用发布标识

Status: implemented

[English](2026-09-05-product-release-identity.md) | 中文

## 问题

独立的原生版本字面量会让同一候选报告不同应用版本。协议和持久化格式版本表达互操作义务，用其中任何一个充当应用发布号都会混淆彼此独立的变化。

## 决策

根包 manifest（元数据清单）拥有应用 SemVer。显式发布元数据拥有构建号和分发渠道；生成器在打包前派生 Android、Apple 和 Windows 表示。解析拒绝与字节新鲜度检查均在产物构建前执行。[参考文档](../../../../docs/development/product-release-identity.zh.md) 拥有字段、限制和命令说明。

应用标识扩展 [npm 发布序列](2026-08-10-npm-release-sequences.zh.md)，不取代其中独立的 vendor 与 native 发布所有权。dsh 版本规划器验证发布元数据，并将生成的平台输入纳入正常提交。渠道选择改变分发元数据，不启用 runtime capability，也不改变协议准入。

未签名的 Windows 打包独立编辑 PE 版本资源。electron-builder 编程接口的 `afterPack` 回调在安装器收集可执行文件之前使用 `resedit`，保留非版本资源和可执行节。这避免了原生资源编辑器工具包解压时在 Windows 上创建 macOS 符号链接的要求。`buildVersion` 和 `buildNumber` 都显式传入，因为 NSIS 独立地从后者派生数字版本字段；环境中的 CI 计数器不能替换发布元数据。该生产者禁用发布，并提供不执行任何证书操作的签名回调；编辑前拒绝已签名输入，防止静默破坏签名。

## 考虑过的替代方案

- 手工原生版本即使在包版本一致时仍可能漂移。
- 从协议版本派生应用版本会耦合兼容性含义不同的发布。
- CI run number 无法从已提交输入重现候选；显式构建号可以。
- 在已提交生成文件中嵌入当前源码 SHA 会形成自引用。候选 manifest 在 checkout 后绑定源码 SHA 和产物摘要。
- 只修改外层安装器或打包后的解包程序，会让实际安装的主程序继续报告 Electron 版本。资源编辑必须早于安装器收集。

## 后果

平台数字限制约束公共标识。新的分发候选必须跨版本和渠道递增构建号；同一产物重试保留原值。[候选完整性验证器](2026-09-06-candidate-artifact-integrity.zh.md)负责与保留分发清单比较。仅解析标识无法证明签名、安装或发布就绪。

必要验证涵盖无效元数据、渠道/版本不匹配、数字溢出、缺失和过期生成物、不写入的发布规划，以及实际平台内嵌元数据。Apple 设置与 Info.plist 比较独立拒绝差异。打包和发布证据与这些源码检查分别保留。
