# Agent Note: Support-bundle value hygiene and the two-platform same-candidate proof

Status: implemented

English | [中文](2026-10-28-support-bundle-value-hygiene.zh.md)

## Problem

The §42/§43 family row closed its sanitizer and collector gaps with three findings. First, the secret-shape scan covered keys only: a free-text value — an error message quoting a curl failure, the most common real-world carrier — could ride a `message` field through `describe()` and the bundle untouched, because the recorder stored raw text and `scanKeys` never looked at string values. Second, the stamped `sourceRevision` was forwarded verbatim: `DSH_BUILD_REVISION` set to any malformed string reached operators as-is, so a misconfigured stamp silently degraded the §42 provenance fact. Third, the §43 same-candidate claim had one implementation witness: the Node producer validated its own artifact, and no second platform re-derived the canonical serialization, the per-entry digests, or the chained checksum — the spec's "four platforms produce byte-identical bundles" was asserted by construction, never proven against an independent port.

## Decision

Three mechanisms, one per finding. (1) Value-level redaction at the ring's single write entry: `redact.ts` names three secret shapes — a `Bearer` credential, an `sk-` key, and an `api-key`/`token`/`password`-style assignment — and `recordError` passes every message through `redactSecretShapedText`, replacing each match with `[redacted:<kind>]` before it ever reaches the ring or a §42 payload. The recorder is the only write path, so no other fact source can bypass it. (2) The sanitizer now refuses values, not just keys: `scanKeys`'s string branch runs `carriedSecretShape` and a value carrying a shape fails the whole bundle loud — redaction is for recorded text the owner controls, refusal is for assembled values the bundle would publish. (3) `readStampedRevision()` accepts exactly a 40-hex commit sha or the literal `source-tree`; the constructor calls it so a malformed `DSH_BUILD_REVISION` fails the plugin's load (misconfiguration fails loud at the earliest resolvable point), and `describe()` re-reads per call so a corrected environment variable takes effect without a reload.

The §43 same-candidate proof is a derived fixture plus an independent Kotlin port. `tests/gen-candidate.mjs` feeds fixed inputs (a diagnostics snapshot with a pre-redacted error, two session-header rows, two settings-export rows) through the production `buildSupportBundle` and writes the sealed artifact — the fixture is derived, never hand-written, so it can never drift from the producer's rules. `SupportBundleCollector.kt` on the companion side re-implements validation with no shared code: strict shape checks, the canonical per-entry serialization (`kind` first, top-level content keys in code-unit order, nested objects in insertion order, JS string escaping with the producer's exact escape set), SHA-256 per entry, manifest order, and the chained checksum. Its JVM test validates the same fixture bytes and re-derives the same chained checksum, plus four tamper shapes — a mutated entry value, a forged chain checksum, a dropped manifest row, an unsorted manifest — that the Node collector's tests refuse with the same outcomes.

## Alternatives considered

Broadening the value scan past the three shapes (URLs, emails, hex blobs) was rejected — every widened shape multiplies false positives, and a support artifact that refuses healthy values stops being collected exactly when it is needed. Sharing the serializer between platforms (KMP module or generated code) was rejected — the proof's value is independence: a shared implementation can only agree with itself, while a from-scratch port agreeing byte-for-byte is evidence the serialization rules are actually pinned in the spec and README. Running the Kotlin lane against a live Host export was deferred — the fixture proof pins the algorithm; wiring collection into the Android export flow follows demand, and the §41 snapshot path already demonstrates the wire fetch. A Swift lane stays out of tree for the same CI-synchronize reason as previous generations: unverifiable locally means not claimed.

## Consequences

The recorder writes only redacted text; the bundle refuses shape-carrying values; a malformed stamp fails load. TS spec is 43/43 (nine new cases: the §42 audit covering the three shapes' redaction in a recorded message, redaction idempotence, and the load-time stamp rejections; the §43 cases covering value refusal per shape and the candidate's self-validation). The Kotlin lane is 5/5 on the JVM against the same fixture bytes; physical-device acceptance and the Swift lane stay on the external ledger, unclaimed. What stays open in the §41-44 family after this generation: only the external acceptance lanes.
