# Agent Note: Handoff L1

Status: implemented

[English](2026-09-01-handoff-l1.md) | 中文

## 问题

Lite 运行时折叠 `handoff/requested` 并显示点名"能力在宿主继续"的横幅——但第 39/40 章的链路（快照 → 选宿主 → 创建记录来源与溯源的新全量会话）并不存在：没有任何东西从设备 Lite 会话跨到宿主，横幅只是没有机制的词语。

## 决策

接力是一个组合式宿主动词加类型化设备侧发送器。`session/handoff`（carrier 白名单 controller 角色，同 fork）接收第 40 章快照——`sourceSessionId`、`sourceRuntime: 'lite'`、`requestedCapability`、`recentContext`（尾部对话逐字）、`planActive`（Lite 计划词汇只是一个标志）、`todo`、`artifactRefs`（仅元数据）、可选 `modelPreference`、以及 `provenance {deviceId, platform, at}`——并组合三条既有命令：`create`（新建 Agent 的路径只有 create、fork 与 handoff）、`rename`（钉住 `设备接力：<能力>`）、与携带宿主从快照渲染的确定性中文简报的 queue 模式 `prompt`。简报——能力、带 ISO 时间戳的设备溯源、计划标志、待办、工件引用、模型偏好、近期行、收尾指令——是首条用户消息，来源与溯源之所以持久，正因为 prompt 日志持久；没有新 SessionEventMap 成员、没有持久化目录变更、没有折叠变更。若没有适配器服务所选 provider，接力经 prompt 既有的 `model-unavailable` 拒绝响亮失败。

设备侧与任何 UI 壳解耦（Lite 聊天面是库层，尚未嵌入）：Kotlin `LiteHandoff` 从折叠的 `LiteDomainState` 构建线快照并经 `WireDriving` 缝发送；Swift `SessionHandoff` 住在 SharedAppleRemoteCore、取扁平入参（行、标志、溯源结构体），因此不需要 LiteRuntime 依赖——LiteRuntime 刻意没有任何依赖——调用点自行适配其折叠状态。两者在拒绝或无会话应答时返回 null，与 `readArtifact` 一致。线词汇走 link-contracts：`LinkHandoffSnapshot` 及其嵌套行以 fixture 钉住真实 `SessionHandoffSnapshot` 类型，再生进 Swift 与 Kotlin。

## 后果

设备现在可以经既有 TLS carrier 把 Lite 会话的上下文搬到宿主：新会话带钉住标题出现、简报作为工作入队，`session/handoff` 是 create 与 fork 之外的第三个白名单创建者。TS 客户端 sessions 面有意不拓宽——web 客户端自身就是全量运行时、从不发起接力，拓宽它只会给无消费者的表面加面（readArtifact 被迫带出的 fake-api/fixture 级联在这里没有触发点）。把链路嵌到 Lite 横幅动作之后（壳接线、跳转会话标签到新 id）仍是未来产品化；它将调用的正是这些组件。第 41 章的排除项保持——无事件导出、无进程收养。

## 考虑过的替代方案

为溯源设专用日志事件被否决——入队简报已忠实持久记录它，新 SessionEventMap 成员会为用户消息已携带的数据波及持久化目录、三个折叠与 SDK 表面。让设备经三个既有端点驱动 create-改名-prompt 被否决——三次往返、三个失败窗口、且没有原子的来源记录；一个动词在服务端组合它们。把结构化快照塞进 prompt 文本（JSON 块当消息）被否决——宿主渲染简报，设备因此免于呈现职责，线保持类型化、契约钉住的形状。
