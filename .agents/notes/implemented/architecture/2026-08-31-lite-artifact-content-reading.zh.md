# Agent Note: 经资源通道读取工件内容

Status: implemented

[English](2026-08-31-lite-artifact-content-reading.md) | 中文

## 问题

第 56 章按设计把工件内容挡在事件之外——引用与状态走 journal、字节住资源通道——而两侧 Lite 运行时都有了通道（`LiteFileArtifactStore`）却没有消费面：没有东西把字节读回来，每个工件都只是列表里的一个名字。

## 决策

两侧运行时在既有通道上获得同一个读取并呈现的函数：`readLiteArtifact(store, reference)` 按 id 取字节并决定呈现——文本类（markdown、text、report、patch）解码后直接呈现内容，其余类别只呈现类型与字节数，缺失的 id 读为缺席的诚实空态（完全没有通道亦然）。聊天视图模型在 journal store 旁以可选注入接收工件 store 并暴露 `readArtifact`；两个面按引用渲染行——Compose 的工件行加了按需"内容"开关（首次打开时读取），SwiftUI 的行在折叠组后随出现读取——呈现文本、`kind 类型 · N 字节` 一行、或 内容缺失。

## 后果

两侧测试对着真实临时目录 store 钉住相同行为：文本类往返到精确文本（markdown 与 patch）、二进制类显示类别与大小（image 1234 字节、file 编码字节数）、缺失 id 读为 null、聊天面经注入的通道读取——有通道返回内容、无通道为 null。两条车道验证全绿。远程伴侣的工件面板按设计保持仅引用：宿主尚未记工件事件，其通道消费随宿主事件一起到来。

## 考虑过的替代方案

把内容内联进折叠被否决——那正是第 56 章禁止的；折叠保持仅元数据、字节归通道。渲染二进制字节（例如图片）被延后——今天线上没有任何工件类别携带面们能解码的图片字节；类型与大小的一行才是诚实的首版。
