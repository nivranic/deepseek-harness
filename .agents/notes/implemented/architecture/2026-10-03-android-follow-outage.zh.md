# Agent Note: 持久化 follow 窗口的载体断开车道（§25）

Status: implemented

[English](2026-10-03-android-follow-outage.md) | 中文

## 问题

载体断开恢复必须在重新附着实时流时保留已加载历史和未发送输入。空闲 follow 无法可靠检测 adb 反向隧道移除，因此该操作不能作为确定性的重连触发条件。

## 决策

- 新车道 `apps/web/tests/android-follow-window-outage.e2e.ts` 沿持久化车道骨架：配对、打开预置 Session、加载一页较早历史、在仍打开的流上追加三条记录并让设备显示（持久截点前移），随后 `terminateDeviceConnections({ deviceId })` 在 Host 侧销毁配对设备的流载体——设备自行检测到的真实传输中断，不涉及 adb 反向隧道移除。
- 重开的 follow 使用原地址与分页上限。断线期间不追加记录；重连后三条新记录通过新流到达，必须无缺口地合并入保留页面。
- 窗口断言采用三步有界重试梯，覆盖两类已观察到的抖动：慢响应被丢弃（driver 单请求计时器到期而 server 侧操作仍完成）与窗口事实已匹配后 Compose 滚动验证器自行放弃——两者均属再观察类。两连绿锚定稳定性。
- 断言未发送输入、单设备授权与零业务写；截图落 `.artifacts/screenshots/android-follow-window/outage.png`。

## 备选方案

- **以 adb 反向隧道移除充当断网：** 否决——§29 断线车道已记录空闲 follow 流检测不到被移除的 reverse 隧道，车道会挂在未检测到的断开上，无法行使重连路径。
- **仅在断线期间追加记录：**完整 opening 能恢复这些记录，但这本身不能证明新实时流的投递能力。本场景在断开前和重连后追加，以检查保留历史及恢复后的实时投递。
- **钉死快照原始记录数：**Host 返回按消息数限制的完整 opening，其中还可能含有元数据。场景检查相同的请求字段、合并连续性和较早历史保留。

## 结果

- 该场景定义载体断开恢复验收。完整 opening 适配需要新的安装态运行；前台/推送行为和真机仍分别验收。
- 拓宽的重试梯（超时+滚动验证器两类）成为负载模拟器上整窗断言的新基线。
