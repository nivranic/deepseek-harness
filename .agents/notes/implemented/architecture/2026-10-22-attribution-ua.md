# Agent Note: The companion's provider requests carry a static User-Agent; the §33 re-projection and combination items close as recorded decisions

Status: implemented

English | [中文](2026-10-22-attribution-ua.zh.md)

## Problem

Gen-56 ([the OkHttp migration note](2026-10-16-lite-http-okhttp-config-face.md)) ruled "attribution headers (`x-deepseek-harness-*`) stay off: those identify the host harness to the provider, a different product face from the companion; the minimal alignment is Bearer, content type, and accept," and the §31 ledger carried the wider form forward as an open item (the attribution-header decision). Two facts pressed on that ruling. First, the host's mandatory attribution rule ([2026-06-21-mandatory-app-attribution-headers](2026-06-21-mandatory-app-attribution-headers.md)) says every product LLM adapter sends a static, non-secret application identity on every provider HTTP request, proven on the wire by a mock server — and `LiteHTTPProvider` is exactly that, the product LLM adapter for the user-configured endpoint, with no carve-out in the rule's wording for a companion-sized adapter. Second, the different-product-face rationale does not hold for traffic identification: it distinguishes the two products to each other, never to the endpoint operator receiving the request, who cannot tell what sent it — and when the operator cannot distinguish sources, `User-Agent` is the only honest channel. A self-configured endpoint benefits the same way (support, abuse investigation, compatibility debugging — the host rule's own use list).

## Decision

Flip the ruling: the request header block in `LiteHTTPProvider.stream` gains a static literal `user-agent: dsh-lite-companion/1.0` beside content-type, accept, and authorization (the name lowercase in code like its neighbors; field names are case-insensitive on the wire). Static per the host rule's wording — never a `BuildConfig` or runtime version read: the host adapters read their version from the owning package manifest through `createRequire`, an npm-workspaces mechanism with no Android equivalent, and a build-derived version would drift per build without adding identifying power. The explicit header also replaces OkHttp's default `okhttp/<version>` token, so exactly one identity reaches the wire. What stays off is the host's `x-deepseek-harness-*` request identity (user and session headers under the DeepSeek-specific decision) — that is host-harness request identity, not product attribution, and the gen-56 sentence's core on that family survives the flip. The existing header-assertion test (the embedded server's received-header pins) grows the User-Agent equality; no new test class. This generation's other half closes the two §33 open items as recorded decisions: preset re-projection is condition-triggered — the excluded list (cordis, ptc, standard, excluded because their assembled sections still reference `{{cwd}}`/`{{model}}`) is the observable face of the trigger, so once a host-side preset sheds its runtime variables, re-running `gen-lite-preset-catalog` harvests it, while substituting values on the Lite side would be the parallel prompt system the specification forbids (original-specification.md:1210); and combining contexts beyond profile/preset is the specification's own limit, not a gap — the spec (original-specification.md:1216-1220) lets Lite combine contexts only through profile/preset, so any extension is upstream specification evolution.

## Alternatives considered

Keeping gen-56's no-attribution ruling was rejected — "different product face" answers which product the traffic belongs to, not how an endpoint operator identifies it, and the host rule's every-adapter wording leaves no companion exception. Reusing the host's `deepseek-harness` User-Agent token was rejected — the companion is a different product with its own request identity, and borrowing the harness token would misattribute companion traffic to the host harness, the same conflation gen-56 named, now in the other direction. A `BuildConfig`-derived version in the token was rejected — the rule asks for static identity, and a per-build version reads as telemetry the rule never requested. Sending the library default alongside a product token was rejected — there is one `User-Agent` field, and the explicit header replaces OkHttp's default rather than stacking on it.

## Consequences

Providers and self-configured endpoints see identifiable companion traffic (`dsh-lite-companion/1.0`) instead of a library default; nothing else on the request face moved — the journal, the fold, and the sixteen-tag closed set are untouched. Core JVM tests stay at 85 suites / 608 tests with zero failures (the User-Agent pin rides the existing `LiteHTTPProviderTest` header test, 11 tests green), and contract stays at 4 suites / 37. The gradle acceptance round (scanner env, `-PdshNativeAcceptance`, the four tasks) came back BUILD SUCCESSFUL in 1m 40s with 82 actionable tasks of which 9 executed; the debug APK drifts past the gen-71 baseline to the new recorded baseline `3cb24ecfc2f5a801d02bb439b35386a3db220050943425efb18f4f8199eeebb6` (the rebuilt core classes repackaging the debug face), while the androidTest APK replays byte-identical at `0fac30016109b0621c672cb13b4d4a777e1baccfa8abcb09c1ca730d26c3eb69` — the private header addition never touches the androidTest packaging inputs. The traceability §33 remaining swaps its two open items for the recorded-decision forms, and §31 drops the attribution-header decision from its open list with the flip recorded.
