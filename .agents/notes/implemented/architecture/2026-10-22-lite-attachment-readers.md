# Agent Note: attachment_read and image_inspect land as the paired Lite attachment readers

Status: implemented

English | [中文](2026-10-22-lite-attachment-readers.zh.md)

## Problem

[The pairing rule](2026-10-18-lite-local-tool-executors.md) left `attachment_read` and `image_inspect` as declared-but-unreachable names — an executor without a same-generation device schema is only hallucination-reachable — and gen-66/gen-67 pinned the deeper blocker: no intake producer, then [the intake](2026-10-22-lite-attachment-intake.md) itself landed with the request-face decision explicitly deferred to this generation, paired with the two executors and their schemas. With the store live, two questions had to be answered together: what the executors read and how, and what admitted attachments mean on the provider request face.

## Decision

Close the pair, and close the request-face question as "the tools read, the prompt never carries". Both schemas join `lite-device-tool-schemas.json` beside declarations that already carried `supportsLite` (both low-risk, empty permissions — the same-generation pairing satisfied in one increment). `attachment_read` parses `{"name": string}`, resolves the entry through the store's listing face (the retained media type lives only there), and routes on it: a textual type — the same vocabulary url_fetch owns, any `text/*` plus the json/xml/yaml/javascript application subtypes and the `+json`/`+xml` suffixes, with the constant renamed from url_fetch-private to the shared `TEXTUAL_APPLICATION_SUBTYPES` — decodes under its declared charset inside a new `ATTACHMENT_READ_CONTENT_LIMIT_BYTES = 64 KiB` cap (refusal, not truncation: the model must never mistake a prefix for the whole document; independent of intake's 8 MiB because that bounds what the device keeps while this bounds one model-turn result); every other type — including a retained media type okhttp cannot parse — refuses as binary naming the stored value; a corrupt sidecar's fail-loud `IllegalStateException` answers as its own fail-soft fact, never a throw into the loop. `image_inspect` parses the same shape, sniffs the bytes' signature — PNG/JPEG/GIF/WebP per the host `read_image` sniffer, plus the HEIF family's `ftyp` major brands (heic, heix, hevc, hevx, heim, heis, hevm, hevs, mif1, msf1) — and reports the sniffed format (the retained media type never reaches this tool), the width and height in pixels, and the stored byte count on one line. The pixel bounds read through the injected `LiteImageBoundsReading` seam returning `LiteImageBounds?`: the executors' module is JVM-only (`kotlin("jvm")`, no android.jar on its classpath), so the BitmapFactory `inJustDecodeBounds` face — metadata without a pixel decode — rides in MainActivity as the private `LiteAndroidImageBounds` object, and the JVM tests stand their own reader in; a null bounds read past a passing sniff answers the same unrecognized-image refusal as a failed sniff. The MainActivity `when(name)` gains both branches over the `liteAttachments` store the lite-open branch already held. The request-face decision this generation owns: admitted attachments are the tools' read face and nothing else — the model reaches them by name through tool calls, tool results feed back as typed history, and nothing admitted ever rides a prompt or a provider request row (the calculator/url_fetch closure pattern; an independent Lite session has no wire to upload over anyway).

## Alternatives considered

Riding attachment bytes, or even a name listing, up in the provider request was rejected — it is the decision gen-67 deferred here, and the tool-call closure already answers it: the model reads by name, the result returns as typed history, and prompt-carried bytes would spend request budget on content the user may never ask the model about. Truncating oversized text at the cap was rejected — a silent prefix invites the model to treat it as the whole document; the refuse-at-cap form matches artifact_create and url_fetch and states the number. Calling BitmapFactory from the executors' module directly was impossible rather than merely unwise — core is a JVM-only module, and moving image_inspect wholesale into the app module would orphan its evaluation from the JVM suite; the injected one-method seam keeps the split at exactly the android-dependent instruction. Consulting the retained media type in image_inspect was rejected — a provider-stated type can misname the bytes, and the sniff is the honest fact. A conformance fixture for the two calls was judged unnecessary — both are the standard tool/call + tool/result shape the fixture family already pins generically, and the metadata line is asserted in the JVM suite.

## Consequences

All five local Lite names now carry executors, schemas, and declarations in pair — the deferred pair in the gen-62 ledger is closed. Every executor branch evaluates under JVM tests (the seam made image_inspect fully testable offline, unlike url_fetch's live transport): LiteToolExecutorsTest 15 -> 23 with eight new — malformed arguments on both readers, absence by name, textual decode in declared and default charsets, the binary refusal naming the retained type (including the intake default and an unparseable type), the 64 KiB boundary, the signature table (all seven positive shapes; text bytes, a truncated GIF header, a RIFF container without WEBP, an out-of-family `ftyp` brand, and empty bytes as negatives), and the metadata line through a fixed bounds reader including the null-bounds and sniff-gate refusals. Core JVM tests: 597 -> 605 across 85 suites, zero failures; contract stays 4 suites / 37 tests. The androidTest face compiles (`:app:assembleDebugAndroidTest`) — no on-device round is claimed, and the BitmapFactory face itself is exercised only there. Admitted attachments remain invisible to the journal, the fold vocabulary, and provider requests — unchanged from gen-67.

## Open follow-ups

The camera intake source stays deferred (gen-67's follow-ups listed it here; it remains outside this increment and needs the paired camera chain's cleanup machinery); the tool-row journal persistence stays a chapter-64 decision; a live on-device image round (real image bytes through BitmapFactory) rides the connected-device acceptance when that lane exists.
