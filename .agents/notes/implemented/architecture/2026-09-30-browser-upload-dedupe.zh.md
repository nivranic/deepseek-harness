# Agent Note: 浏览器 Client 经 uploadDedupe 重新暂存已记忆的上传主体

状态：implemented

[English](2026-09-30-browser-upload-dedupe.md) | 中文

## 问题

按摘要去重的操作（`fileUploads/uploadDedupe`）此前只存在于 Host 与 Android companion。浏览器页面重传自己会话已存储过的主体——回执丢失后、草稿刷新后或重试发送时——仍要把完整字节推过流式载体，为 Host 已持有的字节支付全额传输。

## 决策

浏览器 `FileUploadRuntime` 对可重读主体应用同一记忆探测：

- 模块级 `uploadedDigests` 集合记录本页每次成功上传主体的摘要，与 companion 的进程本地记忆同构。
- Host 声明 `file-upload.dedupe.v1` 且输入是 `Blob` 或精确字节时，runtime 以有界 1 MiB 分块哈希主体（`@noble/hashes` sha2，分块间检查取消），记忆命中的摘要先经 `remote.fileUploads.uploadDedupe` 寻址再启动任何载体。命中时零字节传输即暂存回执，且不报告字节进度。
- `FILE_DIGEST_NOT_KNOWN` 精确回退一次完整上传（成功后重新学习摘要）；其余拒绝原样返回调用方，绝不静默重传。一次性 `ReadableStream` 输入不可重读、从不计算摘要，始终走流式载体；无该能力的 Host 完全跳过哈希。
- 拒绝分支经宽容形态窄化错误，因为 Host 注入的附件拒绝码位于静态声明的失败联合之外。

## 备选方案

- **无记忆、每次上传都探测：**每次首次上传都付一次本地全量读加一次被拒往返，而第二次尝试之前命中率恒为零。
- **把摘要持久化到存储：**页面作用域记忆与回执自身生命周期一致；跨重载记忆会对可能不同的 Host 探测，为没有实测需求的问题引入陈旧摘要缓存。
- **经 `tee` 哈希一次性流：**探测将与传输竞速且仍需把主体完整读两遍；流保持流式契约更合理。

## 结果

- 重传本页已交付过的主体只付一次本地哈希加一次摘要专用 RPC，替代整个载体传输。
- 摘要计算对可重读主体以有界分块多读一遍；没有任何分配随主体规模增长。
- 任何主体的首次上传与既有行为逐字节一致（不探测、不哈希）。

## 未竟工作

- 去重命中路径尚无真实浏览器端到端演练；覆盖为客户端单测矩阵（探测、回退、拒绝对传、能力门）加上传去重增量已封存的 Host 侧 `uploadDedupe` 验收。
- 流式载体本身仍无去重路径；它需要对不可重读的流做派发前摘要。
