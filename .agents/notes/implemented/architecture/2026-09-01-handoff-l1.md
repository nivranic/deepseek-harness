# Agent Note: Handoff L1

Status: implemented

English | [中文](2026-09-01-handoff-l1.zh.md)

## Problem

The Lite runtimes fold `handoff/requested` and show a banner naming the capability continued on the host — but chapter 39/40's chain (snapshot → select host → create a new full Session recording origin and provenance) did not exist: nothing crossed from a device Lite session to the host, and the banner was words without a mechanism.

## Decision

Handoff is one composed host verb plus typed device-side senders. `session/handoff` (controller role in the carrier allowlist, like fork) takes the chapter-40 snapshot — `sourceSessionId`, `sourceRuntime: 'lite'`, `requestedCapability`, `recentContext` (trailing conversation rows verbatim), `planActive` (the Lite plan vocabulary is one flag), `todo`, `artifactRefs` (metadata only), optional `modelPreference`, and `provenance {deviceId, platform, at}` — and composes the three existing commands: `create` (the only new-Agent paths are create, fork, and handoff), `rename` (pinning `设备接力：<capability>`), and a queue-mode `prompt` carrying the deterministic Chinese brief the host renders from the snapshot. The brief — capability, device provenance with ISO timestamp, plan flag, todo, artifact refs, model preference, recent rows, closing instruction — is the first user message, so origin and provenance are durable exactly because the prompt journal is durable; no new SessionEventMap member, no persistence-catalog change, no fold change. If no adapter serves the selected provider the handoff fails loud through prompt's existing `model-unavailable` refusal.

The device side stays decoupled from any UI shell (the Lite chat surfaces are library-stage, not embedded): Kotlin `LiteHandoff` builds the wire snapshot from the folded `LiteDomainState` and sends through the `WireDriving` seam; Swift `SessionHandoff` lives in SharedAppleRemoteCore with flat inputs (rows, flags, provenance structs) so it needs no LiteRuntime dependency — LiteRuntime has deliberately none — and callers adapt their folded state at the call site. Both answer null on refusal or a session-less reply, mirroring `readArtifact`. The wire vocabulary rides link-contracts: `LinkHandoffSnapshot` and its nested rows are pinned to the real `SessionHandoffSnapshot` type with fixtures, regenerated into Swift and Kotlin.

## Consequences

A device can now move a Lite session's context onto the host over the existing TLS carrier: the new Session appears with a pinned title and the brief queued as work, and `session/handoff` is the third allowlisted creator beside create and fork. The TS client sessions face is deliberately NOT widened — the web client is itself full-runtime and never originates a handoff, so widening it would add surface with no consumer (the fake-api/fixture cascade that readArtifact forced has no trigger here). Embedding the chain behind the Lite banner action (shell wiring, session-tab navigation to the new id) remains future productization; the pieces it will call are these. Chapter 41's exclusions hold — no event export, no process adoption.

## Alternatives considered

A dedicated journal event for provenance was rejected — the queued brief already records it durably, and a new SessionEventMap member would ripple through the persistence catalog, all three folds, and SDK surfaces for data the user message already carries faithfully. Letting the device drive create-then-rename-then-prompt over three existing endpoints was rejected — three round trips, three failure windows, and no atomic origin record; one verb composes them server-side. Carrying the structured snapshot inside the prompt text (JSON blob as the message) was rejected — the host renders the brief, so the device stays presentation-free and the wire keeps a typed, contract-pinned shape.
