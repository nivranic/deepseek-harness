# Agent Note: 分页工件读取

Status: implemented

[English](2026-08-31-artifact-paged-reads.md) | 中文

## 问题

两个工件读取面每次调用都往返整内容：模型重读大工件每次把其全部体积付进对话，配对伴侣为了看个前缀也得取回全部字节。工作区文件面早已用 UTF-16 区间解决了这个形状。

## 决策

工件读取词汇逐字采用工作区文件分页术语：可选 `offset`（区间起点，UTF-16 码元，默认 0）与 `limit`（返回码元上限，缺省读到末尾），响应报告 `truncated`（`limit` 是否在末尾前截断）与 `size`（总码元数）。`artifact_read` 增加两个可选整数参数与两个结果字段；`session/artifact` 增加相同请求字段并返回该页的 base64。负区间响亮失败（线上 `ARTIFACT_BAD_RANGE`；会话内稳定的工具错误文本）。契约行与黄金 fixture 增长 `truncated`/`size`，再生进 Swift 与 Kotlin 模型；两个原生 `readArtifact` 消费者透传可选区间，且只有无界读取仍填字节缓存——分页读取返回其区间而不缓存，因为组装页面的面板尚不存在，全内容缓存里的半件工件会是谎言。

## 后果

大工件在每个面都可切片付费；默认全读与之前逐字节等价。此面剩余：二进制工件输入、已存字节的保留策略。

## 考虑过的替代方案

按字节分页被否决——工件内容是模型创作的文本，每个消费者（模型上下文、伴侣解码）都以码元工作；工作区文件面已标准化 UTF-16 码元，对称获胜。按 offset 键缓存页被否决——页缓存是面板策略而非传输策略；在消费者组装区间之前什么都不缓存，模型才诚实。
