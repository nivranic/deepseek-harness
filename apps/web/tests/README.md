# apps/web browser e2e

English | [中文](README.zh.md)

Browser tests drive real Chromium over HTTP. The in-process lane's mechanics — modes, fixtures, goldens, and composition differences from `dsh web` — are documented in [`scaffold.ts`](scaffold.ts) and the [browser e2e Agent Note](../../../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.md).

The [transport failure case](transport-failure.e2e.ts) interrupts a Prompt request in the browser before Host delivery. The real Client displays `gateway/transport-interrupted` and reconnects without resending the mutation. The expected observation pins the visible diagnostic, retained draft, one request through reconnection and a second only on explicit retry, with no accepted user message. It exercises no model or native device.

The [inventory error cases](plugin-inventory-capabilities.e2e.ts) supply an unknown error code through a controlled HTTP Remote envelope. English and Chinese pages retain their localized generic failure and recover the real Loader inventory only after an explicit retry. The [command rejection case](commands-capabilities.e2e.ts) also pins the unmodified Host diagnostic and zero handler executions. These injected responses represent newer-Host errors; they are not old/new application-binary compatibility tests.

The [Approval](tool-reused-id.snapshot.ts) and [Question](question-retry.snapshot.ts) transport-recovery cases start separate processes through `dsh --profile web` with scenario patches. They use recorded Session JSONL as both model input and the expected complete persisted log. HTTP fault injection covers loss before Host acceptance and after acceptance; the Question case also holds one Client's answer while another submits a different answer. The primary fixtures remain read-only, and each process uses isolated settings, credentials and skill roots. Their snapshot lane requires built Client bundles through `DSH_EXAMPLE_MODE=lib`; these checks prove recorded transport behavior, not live model-provider behavior.

The [interaction reply protocol case](interaction-closed.e2e.ts) changes one browser reply to unsupported protocol 3 and receives the real Host rejection. The Client exposes its upgrade state, sends no new negotiation during a 60-second virtual browser-clock advance, and requires manual reconnect plus a new answer to the same pending approval. It does not simulate a binary upgrade, Host sleep or a device transition.

The [stream failure cases](transport-failure.e2e.ts) inject invalid JSON, binary frames and invalid interaction records into a real isolated Host connection. English and Chinese controls suspend automatic retries through a 60-second virtual browser-clock advance, preserve the composer draft, and recover only after an explicit click. The existing interrupted Prompt case retains ordinary automatic reconnect and explicit mutation retry. These are controlled wire failures, not physical network, released-version or native-device qualification.

The [command capability case](commands-capabilities.e2e.ts) uses a real isolated Host and its command registry. Controlled discovery advertisements distinguish catalog access from execution; a controlled delay holds an actual handler response across reconnect. The expected output checks local File availability, Host row withdrawal and restoration, retained submission text, and exactly one handler invocation without automatic replay. It does not verify rollback or live-provider behavior.

The [Goal capability case](goal-capabilities.e2e.ts) seeds a disarmed Goal in a real isolated Host. Controlled advertisements select no access, read-only, edit-only and full support. An actual edit commits before its held response is cancelled by connection replacement; a new editor draft and the message composer survive release of that old response. The expected output checks exactly one edit event and no replay. The Commands case additionally waits for the connection-change notice before asserting retained submission text.

The [Subagent capability case](subagent-capabilities.e2e.ts) starts a real continuable child in an isolated Host and holds its model call with a scripted replay. Controlled discovery advertisements withdraw catalog and prompting support independently while preserving Stop, the selected child and its draft. An actual Stop click produces one durable aborted turn; restoring support sends no prompt and starts no replacement turn. Missing parent-catalog hints keep the resident composer visible and read-only instead of hiding supported interruption. This proves product runtime and browser integration with controlled model output, not live-provider or native-device behavior.

The [Feedback capability case](feedback-capabilities.e2e.ts) seeds a completed assistant message in a real isolated Host without model execution. Controlled advertisements test absent entries, read-only display and independent put, delete and Session-record support. A real put commits before its held reply is cancelled by reconnect; an independently opened replacement draft survives its late release without a stale toast. The scenario then performs one real delete and one Session remark, checking exact log events and no replay. It does not establish live-provider, native-device or mutation rollback behavior.

The [upload capability case](file-upload-capabilities.e2e.ts) uses actual native-picker actions and a real isolated Host. Controlled discovery and raw-response delivery verify independent image intake, stale-picker refusal, cancellation of active and queued work, invalidation of ready receipts, retained drafts and explicit retry without automatic restaging. The Host stores the bytes before delayed responses are released. No model, live-provider or native-device behavior is exercised.

The [plugin inventory capability case](plugin-inventory-capabilities.e2e.ts) reads real Loader entries in an isolated Host. Controlled discovery withdraws the tab and a held first reply crosses an equally capable reconnect. The replacement reads changed Loader rows; releasing the old response preserves its search and expansion. A later withdrawal removes the tab and restoration starts with empty page state while keeping the separate composer draft. It makes no model calls.

The [Dynamic Cordis capability case](dynamic-cordis-capabilities.e2e.ts) defines real Host-only and two-half packages in an isolated Host. Controlled discovery distinguishes read-only inventory, activation, refusal, Stop and Remove. Pending refusal survives inventory reconstruction; reconnect unloads Client code without replaying activation. A real Stop completes at the Host before its held reply is cancelled, and the replacement panel retains its own version selection after release. The case checks exact mutation calls and the retained composer draft, without model requests or live-provider behavior.

## Completion observations

The [home-path fixture adapter](fixture-home-paths.ts) stores exact scenario-owned paths as `{{harnessHome}}` in path fields, tool-argument path properties and read-result `<path>` tags. Before full Session comparison, it expands those explicit expected tokens using the current isolated home and native separators; JSON tool arguments retain valid escaping and original spacing. Capture recognizes native and slash-form Windows paths. Adjacent directories, path suffixes, file contents, unrelated arguments and ordinary prose remain observable. The shared Session normalizer is unchanged, and the [upload recording](../../../snapshots/web/file-upload-round/snapshot.yml) retains its complete expected Session.

The [Cordis recorded lifecycle](cordis-tool-round.e2e.ts) selects its header owner by the actual Host platform: [Windows](../../../snapshots/web/cordis-tool-round-windows/snapshot.yml) pins the shipped PowerShell prompt and tool schema, while [POSIX](../../../snapshots/web/cordis-tool-round/snapshot.yml) retains Bash. Both replay the same recorded model turns through real tools and approval, and compare the complete persisted Session, full prompt/schema sidecars and UI. Platform selection changes no product configuration and removes no assertions. Refresh updates only the selected platform owner; replay never writes either fixture. Windows evidence does not establish a POSIX run or live-provider behavior.

The Question recovery driver waits for the localized preset name after the transcript settles. Preset metadata can arrive after the answer and history; an earlier screenshot can legitimately show the preset id. On failure, the driver saves only the roster response status, error code and the built-in preset's display metadata, so a missing roster can be distinguished from delayed rendering without logging authentication inputs.

The Question driver also injects unsupported and malformed Host discovery versions. It checks the localized failure action, absence of automatic discovery retries and event readiness, then restores discovery and explicitly reconnects before completing the unchanged recorded Session.

Authentication recovery cases clear the isolated browser context cookies, then exercise real Host rejection during rediscovery, a composer submission or a completed Question answer. A second tab performs the existing launch-token exchange; the original tab reconnects explicitly. A rejected Prompt requires explicit submission. A retained answer retries only for the Host's matching pending interaction. An answer accepted before authentication loss, or superseded by an independently authenticated Client while recovery is paused, is not sent again. Each case compares the complete Session against the unchanged fixture. These cases do not wait for cookie expiry or model device revocation.

The Question Host-identity case changes only the advertised discovery and negotiation identity after an answer is lost before acceptance. The replacement connection must reopen the Question without automatically sending the retained answer; a second explicit answer completes the unchanged recording and workspace comparison. This uses one real isolated Host with controlled discovery responses, not two physical Hosts or Device Trust.

Host-readiness cases hold the first real event ready frame. One releases it after the waiting indicator appears and verifies that the same socket becomes ready; another retains it through the configured hard deadline and verifies readiness on the automatically replaced socket. Both complete the original Question recording and compare the full Session and workspace.

The authentication-phase case holds the first two real `host/describe` requests. It observes `Authenticating` in the first handshake and after socket loss, checks the collapsed indicator and absence of business dispatch before initial authentication, then releases each request. The recovered page completes the original Question recording with full Session and workspace comparison.

The connection-phase case holds the first two real ready frames to observe first connection and reconnection separately. It records the ready confirmation, switches the real browser context offline, advances its clock to prove no offline socket attempts, then restores the network and releases the replacement frame. The unchanged Question recording verifies the subsequent conversation and stored Session.

The recorded Approval and Question drivers also reload the page while the first result HTTP request is held. If the Host has not accepted it, the same pending interaction reappears and the test explicitly answers again; the fresh Client does not retain the previous page's completed answer. If acceptance precedes reload, the result stays in the transcript and no question or approval reopens. Reload uses the clean application URL and its existing authentication cookie. Complete Session comparison and workspace assertions cover both cases.

The [interaction cancellation cases](interaction-cancel.e2e.ts) use the shipped Web profile with a local model fixture. They suspend an Approval or Question answer before delivery, after an automatic retry, or through actual HTTP401. A second Client cancels the recorded turn through the public cancellation RPC; during authentication loss it uses an independent cookie context. Persisted errors, terminal records and the absence of the approval marker prove cancellation. Reauthentication does not resend the cancelled answer; a subsequent turn rejects late answers and repeated old cancellation without affecting its new interaction. These are live process tests with targeted durable-event assertions, not complete recorded-session comparisons or live-provider tests.

State-sensitive cases use Workspace, admission, attachment, and model-stream barriers to separate visible intermediate states from completed operations. Details close waits for frame transitions; archive verification assigns an explicit title to the seeded Session and follows that identity across reload. See the [CI fixture synchronization decision](../../../.agents/notes/archived/testing/2026-09-08-ci-completion-observations.md).

These tests boot the real web composition in-process and drive it with real browsers over real HTTP. Chromium runs the full lane; the [model and reasoning picker scenario](declared-reasoning.e2e.ts) also runs in WebKit to cover native mouse focus behavior. [Session replay recovery](session-replay-reload.e2e.ts) also runs in WebKit, sharing the `fresh-round-trip` recording and expected output without rewriting them. It covers active-stream reload, completed-turn reload, and reopening a Session. The lane's mechanics — modes, fixtures, goldens, and the deliberate composition divergences from `dsh web` — are documented in [`scaffold.ts`](scaffold.ts) and the [browser e2e Agent Note](../../../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.md).

After installing workspace dependencies, install the browsers and their system dependencies from the repository root:

```sh
pnpm --filter @deepseek-ai/dsh-web-frontend exec playwright install --with-deps chromium webkit
```

On Linux, `--with-deps` installs dependencies through the system package manager. The persistent CI VM must provide these dependencies through image maintenance; CI installs only the browser binaries, as required by the [failover runbook](../../../.agents/notes/implemented/process/2026-07-26-ci-failover-runbook.md).

Ordinary scenarios begin with no registered Workspace or Session and a durable marker recording a removed default Workspace, so explicit folder-selection scenarios retain control of their cwd. `launchWebScaffold({ firstUse: true })` leaves initialization eligible for startup scenarios.

Same-day message goldens use the shared `WEB_FIXTURE_TIME`: seeded transcripts pass it as `createdAt` and pin the browser calendar with `pinBrowserClock`; scenarios that submit live messages also use `pinHostClock` and restore it after teardown. These clocks advance with real elapsed time while keeping native timers intact, so midnight does not change a scenario's date labels.

Every scenario requires the whole client composition to activate. The product boot only warns about inactive entries outside its required list, but the `watchConsole` tripwire, the [real-host smoke](smoke-real.e2e.ts), and the [assembled jsdom boot](assembled-boot.ts) treat a `web boot: warning` as a failure. No scenario option relaxes this: an inactive plugin in a product composition is a defect to fix.

## Completion observations

State-sensitive cases use Workspace, admission, attachment, and model-stream barriers to separate visible intermediate states from completed operations. Model-picker persistence assertions wait for the saved default, independently of menu closure. Details close waits for frame transitions; archive verification assigns an explicit title to the seeded Session and follows that identity across reload. The [CI test reliability workflow](../../../.agents/skills/dsh-ci-test-reliability/SKILL.md#synchronize-on-state) owns these synchronization rules.

[Idle-submission handoff](idle-submission-handoff.e2e.ts) waits up to the scaffold's 30-second turn-completion budget for Host frames and browser placement. Vitest owns scaffold teardown so a replay-consumption error does not replace the failed scenario assertion.

Plugin-manager and HMR lifecycle switches wait up to `PLUGIN_TOGGLE_SETTLE_MS` (10 seconds) for the Host's profile write and the store's follow-up inventory read, the two steps that republish `aria-checked`; that constant's JSDoc records the measured chain.

Explicit scrolling uses `scrollIntoView` from `support.ts`: it resolves the locator again when its old element detaches and checks connection in the same browser task as native scrolling. Scenarios retain their visibility and geometry assertions after scrolling.

Question-composer resize assertions wait for overflow, the clipping mask, and toggle visibility to agree after CSS scroll timelines update.

[The snapshot after closing a sidebar pane](shortcuts-panels.e2e.ts) moves the pointer outside the controls and waits for hover tooltips to close before capture. Keyboard focus remains on the pane.

[The same-origin terminal case](sidebar-terminal.e2e.ts) waits for the UI-triggered Host close operation before checking process termination. It also checks the first window's process, saved bindings and layout after reload.

## These are Host-face tests

They type-check in the root `tsconfig.host.json`, not in the Client aggregate, because they read Host services directly: `ctx.connection`, the Host `SessionStore`, and `ctx.sessionProjectionCache`. Driving a browser at runtime does not make a file part of the Client program — the two faces merge Cordis `Context` under the same keys with different services, so one program cannot see both. Moving these files into the Client aggregate makes every Host-service access fail to compile.

A new scenario joins both program lists in the same change: its file in the root `tsconfig.host.json` include and in the Client aggregate's `apps/web/tsconfig.json` exclude. That project includes all of `tests`, so a file missing from the exclude compiles as Client code, and the Client compiler gate of `pnpm run typecheck` keeps failing with Host-service errors until it is listed.

## Do not import `@deepseek-ai/dsh-client-*` here

Importing a Client package — a value or a type — pulls its TypeScript project and referenced projects into the Host build graph. Generated Remote declarations are available before package compilation, but this does not make the Host and Client Cordis `Context` declarations compatible. Keep these tests on the Host face and use only the explicit built-client harness exception below.

When a scenario needs a Client-owned constant or pure function, mirror it here instead, next to the commented-out import that names the source module. A drift then surfaces as a missed selector or a stale mirrored value — a loud failure, never a silent pass. `scaffold.ts` follows this rule for the welcome-notice namespace, acknowledgement field, version, and asserted Chinese copy.

The built-client harness is the exception. `assembled-boot.ts` imports `AppWebEntry`, the boot-manifest type, and `RemoteMock`; `assembled-remote.ts` imports the Client test runtime's default responses and `RemoteMock`. These packages are explicit project references for booting the real shell against a test-owned carrier. The chat scenarios mirror `conversationContextKey` in `support.ts` instead of importing its Client owner.

Nothing mechanically enforces this rule; keep it in review.

The [Preset capability browser case](preset-capabilities.e2e.ts) changes only the real Host discovery advertisement and replaces the actual connection. It verifies no preset or directory-opener probe without catalog support, catalog-only viewing, management restoration, and dismissal of an open copy dialog on withdrawal. It also disables preset preferences and suppresses directory probes while only the corresponding Settings capabilities are absent, copies a real preset into a private temporary root without opening its directory, then restores support and verifies path reveal plus a persisted default change. Native opening is disabled by the existing authoring overlay. Its owner-local observation records the exact mutations; it does not execute a model turn or claim Device authorization coverage.

The same capability case withdraws Settings read and document-open support separately, checks that reads and native-open requests remain absent, then restores the document entry. The cold-boot RPC-budget case observes the metadata-derived document action and requires one shared describe call; it does not use a sleep to infer completion.

The Models capability case filters actual Host discovery, verifies absent directory and credential requests, checks independent credential-write and model-discovery controls, and replaces a connection while a credential draft is open. It asserts that the draft is discarded and that no credential mutation or endpoint discovery was sent. The generated draft is never captured in screenshots.

The Workspace operation case in [Host discovery](host-description.e2e.ts) withdraws registry, Session organization and follow capabilities across real carrier replacements. It checks independent controls, absent follow traffic and stale rows, dismissed dialogs, and one real rename after restoration. Its Session content is seeded without a model request; the case does not establish live-provider or Device authorization acceptance.

The directory operation case checks absent picker traffic, browse-only adoption, draft disposal, and a real directory creation committed before connection replacement cancels the waiting request. The Host-created directory remains on disk; the abandoned interaction cannot relist or register it. A fresh interaction explicitly adopts it after restoration. Owner tests separately deliver late decoded results. The scaffold uses the browse backend; native OS dialogs and device permissions are outside this evidence.

The Web-search capability case uses an isolated search-provider credential reference without calling its endpoint. It verifies ordinary Settings persistence without credential API support, metadata/write capability combinations, draft disposal on reconnect, and explicit synthetic-key persistence after restoration. Credentials are checked with boolean containment assertions; raw values are never logged, saved in settings, included in observations, or captured in screenshots. The existing plugin-configuration cases cover the shared staged form with actual Host writes.

The file-resource capability case opens a real workspace file with metadata and observations withheld, restores metadata alone, and replaces the connection after a Host file write. Fresh metadata and the replaced preview registration reload the retained tab without an observation stream. Restoring observations delivers a subsequent instrumented write; withdrawal sends no metadata/feed request, and restoration reopens the held resource. The [file UI capability matrix](file-capabilities.e2e.ts) separately proves absent listing entries, listing-only filenames, text/code fallback, complete-byte image previews, HTML dependency reads, and previews without directory listing through real connection replacement.

The [subagent conversation recording](subagent-conversation.e2e.ts) repeats the browser’s accepted Prompt through real HTTP, both concurrently and after the child has settled. All replies must return the original message id, one inbox insertion must remain, and a cold retry must leave the entire persisted child log unchanged without resuming the child. Existing assembled UI goldens remain read-only. The model responses are recorded replay, not live-provider evidence.

The [subagent Stop recording](subagent-interrupt-ui.e2e.ts) uses the addressed interrupt RPC and resends its first accepted HTTP request while a second child turn is held open. The old target must be acknowledged without stopping that turn; a fresh browser click stops the observed second turn. Existing parked-inbox, FIFO, transcript and composer goldens remain read-only. Parent availability is controlled through catalog responses; the test does not prove a physically disconnected parent, device authorization or live-provider behavior.
